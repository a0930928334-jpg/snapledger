# ADR-011：PDF 对账单在本地确定性解析，作为每月的权威校准（v1.1）

- 状态：已采纳（决策第 5 条"对账单永远不发给 AI"已被 ADR-014 取代）
- 日期：2026-10-18

## 背景

M0 阶段发现：汇丰英国可以导出 PDF 格式的月度对账单（Statement）。观察到的结构特征：

- **文本 PDF**（银行系统生成，带字体和文字层），不是扫描图片，可以直接提取文字和坐标。
- 列：日期、类型代码、描述（2–3 行）、支出、收入、余额。
- 日期只出现在每天的第一行；余额只出现在**每天的最后一行**，也就是日终余额，和 App 截图的含义一致。
- 类型代码：`)))` 非接触支付、`VIS` 刷卡或网上支付（境外交易多一行 `INT'L …`）、`BP` 转出给个人（第二行是附言）、`CR` 入账、`TFR` 转账；以后可能还会见到 `DD`、`SO` 等。
- 一天的交易可能跨页；每页首尾有 `BALANCE BROUGHT FORWARD` / `BALANCE CARRIED FORWARD` 行。
- 首页有期初余额、收入合计、支出合计、期末余额。
- 首页还有姓名、地址、账号、sort code、IBAN、BIC，**比截图敏感得多**。

对账单一个月才出一份，而用户每两三天到一周就导入一次，所以对账单替代不了截图。

## 决策

1. **MVP 不变**：主流程仍然是"截图 → AI → 导入格式 v1"。
2. **v1.1 增加"导入 PDF 对账单"（IMP-16）**：在 App 里**本地、确定性地解析**，不经过 AI，也不联网。
3. 对账单作为**每月一次的权威校准**：
   - 和数据库里已有的记录（主要来自截图）按"日期 + 方向 + 金额"匹配，再用当天的日终余额确认。**不用描述做指纹**，因为对账单和 App 里的描述截断方式不同。
   - 对账单里有、数据库里没有的 → 列为"补录"；数据库里有、对账单里没有的 → 列为"可疑"（可能是 AI 抄错或重复导入）；金额不一致的 → 标红。
   - 和截图导入一样，先进预览页，确认后才写入。
   - 用首页的期初、期末余额和收支合计校验解析结果，对不上就拒绝导入，并提示"解析器可能不支持这个版式"。
4. 解析器只认识汇丰英国的版式。解析结果先转成和导入格式 v1 等价的内部模型（`extractedBy = "app"`），后面的对账、分类直接复用。
5. **对账单永远不发给 AI**，提示词文档里也写明这一点。账号、sort code、IBAN、姓名、地址在解析时直接丢弃，不进入数据库。

## 理由

- **准确**：确定性解析没有识别误差，有合计数兜底，可以作为截图识别的"标准答案"。
- **隐私**：对账单包含完整的账户信息，本地解析可以避免上传；符合 ADR-002（不联网）。
- **符合 ADR-003 的分工**：AI 只是截图这条路径的抄写员；有结构化数据源的时候，App 不需要 AI。
- **不打乱节奏**：放在 v1.1，M1–M6 的范围不变；M1 的引擎（对账、分类）可以直接复用。

## 考虑过的其他方案

| 方案 | 不选的原因 |
|---|---|
| 把 PDF 发给 ChatGPT / Claude，输出导入格式 v1 | 不用写代码，但要上传账号、地址等敏感信息；而且文本 PDF 本来就能精确解析，用 AI 只会引入误差 |
| 只用对账单，放弃截图 | 一个月才导入一次，达不到"随时看清钱花在哪"的目标 |
| 放进 MVP | MVP 范围扩大，M2 之后的进度都要后延；截图流程本身已经有对账兜底 |
| 用 OCR 识别 PDF | 文字层已经存在，没必要 |

## 后果

- v1.1 要引入 PDF 库：JVM 端用 Apache PDFBox，安卓端用它的安卓移植版（具体库和版本到时候再查证）。PDF 解析放在 `data` 模块或单独的 `statement` 模块里，不放进 `core`，保持 `core` 是纯 Kotlin。
- 汇丰改版式时解析器要跟着改。测试只用**虚构的、按同样版式生成的** PDF 样本，真实对账单不进仓库。
- M0 的提示词实测可以直接用对账单当标准答案：截取同一时间段的 App 页面，把 AI 的输出和对账单逐条自动比对（只在本地进行，结果不写进仓库）。
