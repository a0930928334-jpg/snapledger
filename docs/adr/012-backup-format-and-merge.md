# ADR-012：加密备份的文件格式和合并规则

- 状态：已采纳
- 日期：2026-10-19

## 背景

MVP 不联网（ADR-002），电脑和手机之间靠手动导出、导入加密备份来同步（SEC-04、SEC-05）。两台设备都会各自导入截图，所以合并时不仅要处理"同一条记录被两边修改"，还要处理"两边各自导入了同一批截图，生成了 id 不同的同一笔交易"。

## 决策

### 文件格式（`.slbackup`）

```
"SLBK" | 版本 u8 = 1 | KDF u8 = 1（PBKDF2-HMAC-SHA256）| 迭代次数 i32 | salt 长度 u8 | salt | nonce 长度 u8 | nonce | 密文 ‖ GCM tag
```

- 密钥 = PBKDF2-HMAC-SHA256(密码, 16 字节随机 salt, 600,000 次)，256 位；加密用 AES-256-GCM，12 字节随机 nonce。
- **整个明文头部作为 GCM 的附加认证数据（AAD）**：改动头部（比如把迭代次数改小）和改动密文一样会导致解密失败。
- 明文是 JSON，包含所有表的**所有行，包括软删除的行**，这样删除也能同步。
- 实现只用 `javax.crypto`，放在 `data` 模块里桌面端和安卓共用的 `jvmShared` 源码集中。
- 已知答案测试的期望值由 Node.js 的 `crypto` 模块独立生成，不依赖 JDK 自己验证自己。

### 合并规则

| 表 | 匹配方式 | 冲突时 |
|---|---|---|
| 交易 `txn` | 按 `id` | `updated_at` 较新的为准，删除（`deleted_at`）也一样 |
| 交易，id 本机没有 | 按**指纹计数**：本机有同指纹、且备份里没有的有效交易时，视为两边各自导入的同一笔，跳过 | — |
| 日终余额 | 按（账户，日期），因为两边各自生成 id | 较新的为准 |
| 分类规则 | 按 `pattern` | 较新的为准 |
| 账户、导入批次 | 按 `id` | 较新的为准 |

所有写入在一个数据库事务里完成；同一份备份合并两次，第二次不产生任何变化。

## 理由

- **按指纹计数**和导入时的去重（ADR-005）是同一个思路：同一天两杯相同的咖啡，两边各有两条，合并后还是两条，而不是四条或一条。
- 余额和规则用自然键而不是 id，是因为它们本身就有唯一约束（同一天只有一个余额、同一个商户只有一条规则），按 id 合并会违反约束。
- 较新的为准（last-write-wins）简单、可预测，对单用户、两台设备、手动同步的场景足够。

## 考虑过的其他方案

| 方案 | 不选的原因 |
|---|---|
| 只按 id 合并 | 两边各自导入同一批截图会产生重复交易 |
| 导出整个 SQLite 文件、导入时直接覆盖 | 会丢掉另一台设备上的修改 |
| 用 zip + 密码 | zip 的传统加密很弱；AES zip 各家实现不一致 |

## 后果

- 两台设备的时钟偏差会影响"较新的为准"。手动同步、修改间隔通常较长，可以接受；v2.0 做同步服务时改用服务器时间或版本号。
- 跳过的交易不会把对方的 id 带过来，所以两边同一笔交易的 id 永远不同。这不影响结果，因为后续合并依然会按指纹匹配。
- 忘记密码就无法恢复备份，界面上已经明确提示。
